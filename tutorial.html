The Problem

The format gap

You've built something worth knowing. Maybe it's a custom workflow, a tool you wrote, a process your team spent months perfecting. Now comes the part everyone dreads: sharing it in a way that actually transfers the knowledge.

Videos are passive — you watch, but you don't practice. Blog posts are static — you read, but nothing responds to you. What's missing is the middle ground: something you can interact with, make predictions in, get wrong, and try again.

That's what a Tutorialinator tutorial is. The one you're in right now was generated from a 17-minute screen recording using a single command.

The Output

One file. No server.

Every tutorial is a single self-contained HTML file. One <style> block. One <script> block. Zero external dependencies beyond a Google Fonts link. Open it in a browser. That's it.

No npm install. No dev server. No hosting setup. You can email it, put it on a shared drive, host it on a static CDN, or just open it locally. The portability is deliberate — sharing the file is sharing the knowledge.

Everything computation-heavy runs on your machine. Whisper transcribes locally, FFmpeg processes frames locally, Playwright validates locally. The only external call is to Claude's API. Your data stays on your device.

Architecture

Local first, always

Every computation-heavy step runs on your machine. Whisper is a neural network that runs locally — your video audio never leaves your computer. FFmpeg processes frames locally. The only external call is to Claude Code (which handles its own privacy guarantees).

This was a deliberate design choice. A tool that processes your screen recordings, code, and internal processes needs to earn trust. As Masud described in the video: "trust was a big deal to me — I wanted to ensure that as I was building this it was as local as possible."

🎙

Whisper

OpenAI's local speech-to-text model. Runs entirely on your machine. Transcribes audio with word-level timestamps. The "base" model is ~140 MB; "large" is ~1.5 GB.

🎞

FFmpeg

Extracts frames from video at scene boundaries. Each frame is analyzed visually by Claude to detect code, UI states, and key moments. Auto-installed via Homebrew on macOS.

🌐

Chromium

Playwright's browser, used only during E2E validation after the tutorial is generated. Catches console errors, broken widgets, and rendering failures — things visual inspection misses.

Two MCPs

The two control planes

An MCP (Model Context Protocol) server is a local process that gives Claude new tools it can call. Tutorialinator installs two. They are not interchangeable — each has a distinct role in the pipeline.

🎬

tutorialinator MCP

Python FastMCP server (879 lines). Provides 8 tools: download_video, transcribe_with_timestamps, detect_scenes, extract_key_frames, detect_code_in_frames, generate_chapters, extract_slides, get_video_metadata. Used across Video, Audio, and Slide Deck modes.

Video analysisWhisperFFmpeg
🎭

playwright MCP

Browser automation server. Runs after HTML generation. Loads the tutorial in Chromium, checks console errors, tests chapter navigation, clicks quiz options, runs sandboxes, verifies XP increments.

Learning Design Phase
For every chapter, Claude defines: a measurable learning objective (Bloom's taxonomy L3+ — application, not recall), 1–3 common misconceptions, the key challenge widget, prerequisite concepts, and a widget plan. This is the pedagogical backbone. No HTML is written yet.

Pedagogical Review (sub-agent)
A separate agent reviews the chapter plan against 6 criteria: recall-only quizzes, missing exercises, passive widgets, scaffolding gaps, untested misconceptions, vague objectives. It returns a priority list of fixes. The skill integrates the feedback before writing HTML.
Agent team · Review criteria

The tutorial is written in phases — a locked design system (25+ CSS variables, 8 required keyframes) first, then chapter by chapter. Why phases? Before Playwright runs, a Node.js script checks the HTML structure: are all chapters properly nested? Are there orphaned sections? Are chapter tags balanced? This catches nesting bugs that produce zero console errors but silently break navigation.

Context

What you tell it changes everything

Context isn't just background — it's instruction. The skill uses everything you provide to decide which widgets to build, what to quiz on, what to assume, and what to explain. Without good context, the three most common output failures emerge: code sandboxes get omitted (the agent skips them when the topic isn't obviously "code"), quiz questions test recall instead of understanding, and keyframes get dropped. These are the highest-value additions to any invocation.

Include / exclude the video

By default, Video Mode embeds a recreated visual experience. Add "include the video in the tutorial" or "skip embedding video frames" to control this explicitly.

Widget hints

You can request specific widget types: "include a drag-and-drop reorder challenge", "build a live code sandbox for the deploy step", or "no quizzes, just interactive walkthroughs".

What to focus on

Long videos often wander. Tell it: "focus on the authentication section, skip the setup walkthrough". The skill will weight the transcript accordingly.

What to skip

If parts of your video are off-topic, off-brand, or just filler, say so: "ignore anything after minute 12 — that was troubleshooting noise".

The Problem

Why this exists

I wanted to take a cotidian task — something that's done repetitively, which is sharing knowledge — and share it in a way that it can be actually useful and digestible to other people. Not just yet another video, not just yet another blog, but another medium where folks can interact with it and play with it. A low stakes, noisy, gamified environment for learning. The idea was to take a task that normally requires pedagogical expertise, visual intelligence, and taste — and codify it into a skill that could be repeated easily.

The status quo for knowledge sharing inside teams typically looks like this: someone records a Loom, posts it in Slack, and it's never watched twice. Or someone writes a Confluence doc that becomes stale within weeks. The knowledge exists, but the format doesn't serve the learner. Videos are passive — you watch, but you don't practice. Blog posts are static — you read, but nothing responds. Slides decay the moment the presenter leaves the room.

The question I started with wasn't "can AI generate tutorials?" It was more specific: can an agentic workflow take a knowledge source — a screen recording, a topic, a set of URLs — and produce something interactive, pedagogically sound, and portable enough to just send as a file?

An agentic workflow was promising because the task requires multiple specialized capabilities that no single tool handles well: video analysis (speech-to-text, frame extraction), pedagogical design (learning objectives, Bloom's taxonomy), visual design (responsive layout, animations, interactivity), and quality verification (E2E testing, structural validation). An LLM can orchestrate all of these — but only if you give it the right tools.

If you're building something similar — a system where an LLM orchestrates multiple tools to produce a complex artifact — the rest of this post walks through every decision, prompt, and failure in enough detail that you could rebuild it.

System Design

Architecture decisions

I didn't want something that could just rely on the LLM itself. I wanted something that allowed the LLM to be an orchestrator — which it's incredible at — and pull in other tools. So I started thinking about MCPs and how I could amplify the LLM's capacity. The system ended up with three main components: a skill file (SKILL.md — the 1,679-line specification that tells the LLM what to build and how), an MCP server (Python, handles video analysis and frame extraction), and an E2E validation layer (Playwright, tests the output in a real browser). The LLM I used is Claude (via Claude Code as the IDE). Here's how the architecture took shape.

Decision 1: Single HTML file, not React. The first prototype used React + TypeScript. It was too heavy — the LLM spent more time managing the build system than designing the tutorial content. I didn't want it to focus on building a whole React project — that was just too heavy for what I wanted. It could spend more time focusing on just the pedagogy. A single HTML file with inline CSS and JS is something an LLM can validate end-to-end in one pass. It's also fully portable: send the file, open in a browser, done. No npm install. No dev server.

Decision 2: Local-first processing. Whisper runs locally. FFmpeg runs locally. Playwright runs locally. The only external call is to Claude's API. A tool that processes screen recordings of internal team workflows needs to earn trust — the data stays on the user's machine.

Decision 3: Locked design system. Before I locked the CSS, every tutorial looked different. Some had 4px border-radius, some had 16px. Some used purple accents, some used blue. The "creative freedom" was actually a quality liability. The fix was prescriptive: I defined 25+ CSS custom properties, 8 required keyframes, and specific layout patterns in the skill spec. The LLM copies these verbatim — it no longer decides font sizes, colors, or spacing. The cognitive budget goes to pedagogy instead. This was counterintuitive but immediately improved output consistency.

Decision 4: Two MCPs, not one. Building the MCP was pretty neat — I was pretty much building a tool for the LLM to use on itself. The tutorialinator MCP handles video analysis (Whisper, FFmpeg, scene detection). The playwright MCP handles E2E validation. Keeping them separate means the video tools don't need browser automation dependencies, and the browser tools don't need Python ML dependencies. The tutorialinator MCP is a Python FastMCP server (879 lines) with 8 tools:

download_video · transcribe_with_timestamps · detect_scenes · extract_key_frames · detect_code_in_frames · generate_chapters · extract_slides · get_video_metadata

It also exposes the full SKILL.md as an MCP resource, so other MCP-compatible LLM clients can read the spec and use the same workflow.

If you're replicating this: The key insight is that the LLM needs tools it can't do itself (video transcription, browser testing) exposed via MCP, and everything else (HTML generation, pedagogical design) should be specified in the skill file, not coded into the server. Keep the server thin — it's a bridge to system capabilities, not a logic layer.

Prompt Documentation

The prompts that built this

This is the section I'd want to read if I were trying to build something similar. The skill itself — SKILL.md, now 1,679 lines — started as maybe 200 lines. Through 21 commits over 10 days, it grew as each generation run revealed gaps. The prompts below are the story of how that happened.

1. The idea

I started with what I wanted as an end user. Not the architecture, not the tech stack — just the experience I wanted to create. "Interactive" was the word I kept coming back to.

I want to create a skill that's able to take videos and create rich, interactive tutorials from them. A user should be able to take a video — or a topic — send it to this skill, and have it generate rich interactive content. Quizzes, challenges, gamification. Not a static page. Something people can interact with and play with and maybe get some insight into the creator's thinking. I want to take a cotidian task — sharing knowledge — and make it something people actually engage with.

2. The React attempt

My instinct was React and TypeScript — that's what I knew. It felt like the natural choice for something interactive.

Let's build this as a React TypeScript project. I want a component-based tutorial system with state management for quiz progress, gamification tracking, and chapter navigation. Set up the project structure, routing, and a build pipeline.

3. The pivot question

React was too heavy. The LLM was spending more time managing the build system — directory structure, file imports, TypeScript config — than designing the tutorial content. I was burning tokens on infrastructure instead of pedagogy. So I asked.

We tried building this as a React project and it's just too heavy for this use case. The LLM is spending more time on the build system than on the actual learning content. I'm thinking about pivoting to a single self-contained HTML file — one style block, one script block, no build step, no dependencies. Something an LLM can validate end-to-end in one pass. What are the trade-offs? Is it easier for the LLM to work with a single HTML file? Would we lose anything important by dropping React?

4. Going single-file

The answer convinced me. A single HTML file is something the LLM can reason about completely — no jumping between files, no build artifacts. It's also incredibly portable: send the file, open in a browser, done. No npm install. No dev server.

Let's do it. Pivot to a single self-contained HTML file. One style block, one script block, everything inline. The output should be fully portable — someone should be able to just open the file in a browser. The only external dependency should be Google Fonts. Everything else local and self-contained. Rebuild the skill spec around this constraint.

5. Building the MCP server

I didn't want the LLM to just guess what was in a video. I wanted it to really understand it — frame by frame, word by word. I started thinking about MCPs and how I could amplify the LLM's capacity. Building this was pretty neat — I was pretty much building a tool for the LLM to use on itself.

I need the LLM to be able to truly analyze videos — not just guess what's in them. Can you build a Python MCP server using FastMCP that gives it real capabilities? Transcribe the audio using local Whisper for speech-to-text, detect scene changes with FFmpeg, extract key frames and encode them so the LLM can actually see what's on screen. Everything should run locally — trust and privacy are non-negotiable. The user's data stays on their machine.

6. Adding E2E verification

Generating the HTML wasn't enough. I needed the LLM to see what it built — actually render it, click things, check the console. Not just validate code, but validate the experience.

I also need the LLM to be able to verify what it produces. Not just look at the code — actually see the rendered output in a browser, check the console for errors, click buttons, verify that navigation works. Can we set up a Playwright MCP for end-to-end testing? It should be able to take screenshots, check for content leaks between chapters, and verify interactive elements actually function. I want two separate MCPs — keep the video tools and the browser tools independent so their dependencies don't tangle.

7. Locking the design system

Every tutorial looked different. Some had 4px border-radius, some had 16px. Some used purple, some used blue. All those little decisions around style — is this text larger than that, are these in rows or columns — were adding up and dragging the cognitive load of the model. I needed to take away its autonomy on aesthetics so it could focus on learning.

The outputs look inconsistent — every tutorial has different spacing, colors, border-radius, font sizes. I want to lock the design system. Define CSS custom properties, required keyframes, and specific layout patterns that get copied verbatim into every output. The LLM should not decide font sizes, colors, or spacing. Take away its autonomy on style so it can spend its cognitive budget on pedagogy instead. What CSS variables and keyframes should we define to make every output look like part of the same series?

8. Solving the output size problem

A single tutorial is 1,500–2,500 lines of HTML. Claude's output token limit means it can't write that in one pass — tutorials kept cutting off mid-JavaScript. I needed a phasing system.

We have a problem. The output file is going to be 1,500–2,500 lines and it's exceeding Claude's output token limit — tutorials keep cutting off mid-code. How should we handle this? I'm thinking some kind of phased generation — maybe the CSS and boilerplate first, then chapter by chapter, with validation between each phase so nothing gets lost. What's the best way to structure this?

9. Testing and finding failures

I generated about six tutorials and started looking at them critically. Some things were great — brace balance was perfect in every output, quizzes showed up consistently, the design system held. But code sandboxes were missing in half the outputs, keyframes kept getting dropped, and the quizzes in video-mode tutorials were just testing recall. "What protocol does X use?" — where the answer is literally in the paragraph above. That's not teaching anyone anything.

I've generated about six tutorials now and I'm seeing patterns in what's failing. Code sandboxes are missing in half the outputs — the agent seems to skip them when the topic isn't obviously "code." The confettiBurst keyframe keeps getting dropped. And the quizzes in video-mode tutorials are just testing recall — the answer is literally in the paragraph above the question. These aren't teaching anything. What should we add to the skill spec to address each of these failure patterns?

10. The pedagogical review agent

The generation agent couldn't effectively review its own work. I needed a second pair of eyes — another agent that comes in after the learning design phase and audits the plan before any HTML gets written.

After the learning design phase, I want to spawn a separate review agent before any HTML generation starts. It should audit the plan for: recall-only quizzes, missing interactive exercises, passive widgets that don't require learner input, scaffolding gaps where difficulty jumps too fast, untested misconceptions, and vague learning objectives like "understand X" instead of measurable actions. It should return a priority list of fixes. Can we build this into the skill workflow?

11. Quiz quality enforcement

The review agent helped with scaffolding and missing exercises, but video-mode quizzes were still weak. I needed a more specific check — something grounded in learning theory that the agent couldn't argue around.

The quiz quality in video mode is still the weakest dimension. I want an explicit rule: quiz questions must require Bloom's taxonomy Level 3 (Application) or higher. The learner must apply, analyze, or evaluate — not scan for the answer in the text above. Add this check to the pedagogical review: "Can this question be answered by someone who understands the concept but never watched this specific video?" If the answer is no, rewrite the question. How do we enforce this without making the prompts brittle?

12. Self-healing install

I really wanted a self-healing experience — the user clicks something and it's smart enough and agentic enough to heal itself and keep going. No manual Python setup, no MCP configuration, no "please install X" error messages.

I want the setup experience to be self-healing. When someone installs this, it should verify the Python virtual environment, configure the MCPs, and set up Playwright — and if anything is broken, fix it automatically before continuing. The user should never see a setup error. Build an auto-setup script that runs before every tutorial generation and heals itself. I also want a one-line curl install — someone should be able to pull this from GitHub and have it running with a single command.

13. Open sourcing

The tool worked. I wanted the documentation to be as replicable as the tool itself.

Let's make this open source. Push it to GitHub. Write an install script, an uninstall script, and a README that explains what this is, how to install it, and how to use it. The README should be good enough that someone who's never seen this can get it running. Include the architecture diagram. Add an MIT license. I want this to be something people can actually pick up and use — or fork and adapt for their own skills.

14. Designing the benchmark

I kept finding the same failure patterns over and over. I needed a way to measure quality systematically — not before building, but after. The rubric should come from the failures I'd already seen.

I need a way to measure the quality of what this produces. I want to design a benchmark rubric based on the actual failure patterns we've seen — not hypothetical ones. It should cover technical correctness, design fidelity, interactive elements, and pedagogical quality. Each dimension needs clear scoring anchors so I know what a 3 looks like versus a 5. I also want the agent to be able to self-assess against this rubric at the end of a generation run — and then tune the skill based on where it scored low. Can you help me design this? I want it to be a living benchmark — something that evolves as the system improves.

Those 14 prompts, adapted and refined over 10 days and 21 commits, produced the 1,679-line SKILL.md, the MCP server, the install scripts, the benchmark rubric, and the workflow that ties them together. The skill didn't start at 1,679 lines — it grew because each generation run revealed gaps, and each gap became a new constraint.

If you're replicating this: Start with your user story — what should the end user be able to do? Then build, test, find failures, and add constraints. Don't try to write the perfect spec upfront. The generate → evaluate → constrain → regenerate loop is the whole methodology. Copy prompt 1, paste it into Claude Code, and go from there.

Frustrations and bottlenecks — the honest parts:

Output token limits were the biggest recurring frustration. A typical tutorial is 1,500–2,500 lines of HTML. Claude's output token limit means this can't be written in one pass. The phased generation system solves this — CSS first, then chapter by chapter, with validation between phases — but it adds complexity and occasionally produces seam artifacts where one phase's output doesn't perfectly match the next.

Cross-device install failures cost me a day. The install script initially used set -euo pipefail, which caused silent failures on some systems when a non-critical command returned non-zero. Fixed by switching to set -u and handling errors explicitly. 8f8f868

macOS filename quirks: Screen recordings on macOS include U+202F (narrow no-break space) before AM/PM in filenames. It's invisible in Finder but breaks path resolution in Python. Required a dedicated resolve_video_path function in the MCP server. This one took hours to debug because the error was "file not found" and the file was clearly right there.

Truth and accuracy is the hardest problem. In video mode, the LLM occasionally generates content that wasn't in the transcript. There are times when it's produced things that are just not true — it created a bunch of things that I didn't say in my video. Can't have that. The pedagogical review agent is supposed to cross-check, but this failure mode is structural to how LLMs work and requires ongoing vigilance.

Benchmarking

Measuring what matters

The benchmark was designed after the first batch of tutorials, not before. That sequence matters — the rubric was shaped by real failures I'd already observed, not hypothetical ones. If you're building a similar system, I'd recommend the same approach: generate first, then design your evaluation around the actual failure modes you see.

The full rubric is documented in tutorialinator-benchmark.md (422 lines). Here's how I designed it and what it revealed.

Step 1: Define dimensions. I chose four equally-weighted dimensions based on the failure modes I'd observed:

A — Technical Correctness (25%): Can the tutorial run without errors? Checks brace balance, all 8 required keyframes (fadeUp, shake, confettiBurst, timerArc, particleBurst, charReveal, fadeIn, scaleIn), valid chapter structure, and ID resolution. Scored 1–5 with clear anchors: a 5 means everything present; a 2 means missing chapter structure or 5 or fewer keyframes.

B — Design System Fidelity (25%): Does it look like a Tutorialinator output? Checks for 7 required UI elements: CSS variables (--bg), noise overlay (body::after), Google Fonts link, sidebar, cursor glow, scroll progress bar, and toast notification. A 5 means all 7 present.

C — Interactive Elements (25%): Can the learner do something, not just read? Each chapter should have at least one challenge element (sandbox, config editor, drag-and-drop, decision scenario) AND a quiz AND the XP system AND 3D card tilt. Important nuance: I wrote into the rubric that a low sandbox count alone doesn't lower the score if an equivalent interactive widget fills that role. Human judgment is required here.

D — Pedagogical Quality (25%): Do quiz questions test understanding or just scanning? This is human-scored using Bloom's taxonomy. For each quiz question, I ask: "Could a learner answer this by scanning the 3 paragraphs before it?" If yes, it's recall (L1/L2). If it requires applying a rule to a new scenario, it's application (L3+). A 5 means all questions are L3+.

Step 2: Set pass criteria. A passing output must score at least 3.0/5.0 on every dimension and at least 3.5/5.0 overall. I also defined hard-fail gates that disqualify an output regardless of other scores: file under 20KB (it's a stub), zero quizzes, zero chapters, or all keyframes missing.

Step 3: Select test cases. I picked three tutorials to span the quality range:

1. css-grid (Topic mode, 69KB) — the "typical good case," a technical topic with natural widget opportunities

2. goose-extensions (Video mode, 41KB) — the edge case where multiple spec requirements were dropped

3. prototyping (Video mode, 88KB) — a counterpoint: technically strong with the best quiz quality, but with the same sandbox gap as the failure case

Step 4: Run automated checks, then score manually. The automated checks run on all outputs:

The goose-extensions failure concentrated in two dimensions — interactive elements (zero sandboxes, missing sidebar) and pedagogical quality (both quiz questions were pure recall). The prototyping tutorial is the interesting case: it had the best quiz quality in the entire batch (all 5 questions at Bloom's L3+) but the same sandbox gap. That told me these two problems are separable — fixing quiz quality doesn't fix sandbox omission, and vice versa.

Step 5: Identify systematic failure patterns. Three patterns emerged across all outputs:

Failure 1: Code sandboxes systematically omitted (3/6 outputs, 50%). When the topic isn't "obviously runnable code," the agent treats the sandbox as optional. A Goose extensions tutorial should have a YAML config sandbox; a prototyping tutorial should have a prompt-builder. But neither is "code" in the traditional sense, so the agent skips it. The fix I added to the spec: explicit guidance that "sandbox" doesn't mean "code editor" — it means "structured input area relevant to the topic."

Failure 2: confettiBurst keyframe missing (3/6 outputs, 50%). This keyframe is only used for the quiz correct-answer sparkle effect. When the agent writes quizzes with a slightly different feedback pattern, it omits the keyframe as "unused." Low functional impact, but the polish gap is real. The fix: move it into the required keyframe block that gets copied verbatim before any chapter content.

Failure 3: Video-mode quizzes test recall, not understanding (all video-mode outputs). This is the most educationally significant failure. Quiz questions in video-mode outputs ask about specific facts from the transcript. Example from goose-extensions: "What protocol do Goose extensions use to communicate?" The exact phrase "Model Context Protocol (MCP)" appears in the sentence directly above the quiz. A learner answers in 3 seconds by scanning up — no understanding required.

Compare that to the prototyping tutorial's strongest quiz: "You asked your AI tool to build a transaction categorization system. Its plan has 4 rules but no error handling for edge cases. What is your best move?" This requires applying a design principle to a new scenario. No scanning helps.

The fix I added to the spec: an explicit check in the pedagogical review prompt — "Can this question be answered by someone who understands the concept but never watched this specific video? If no, rewrite it." It helps, but video-mode quizzes are still the weakest dimension.

The living benchmark. Benchmarking is this living thing — because the agent can modify the skill at the end of the process once it's been assessed, it can be honest and say "here are the pieces in the skill that I need to work on." That's going to cause some drift, but it's a worthwhile exploration to see how the system can self-improve — not for reward chasing, but for genuine improvement. The benchmark log tables in tutorialinator-benchmark.md are designed for exactly this: one-shot scores, then two-shot refinements after targeted fixes.

If you're designing your own benchmark: Start from your actual failures, not from theory. Score with clear anchors (what does a 3 look like vs. a 5?). Include both automated checks (fast, reproducible) and human scoring (catches quality issues machines can't). Build in hard-fail gates to catch degenerate outputs. And design the rubric so the agent can eventually self-assess — that's the path to a self-improvement loop.

Reflection

Looking back

Building Tutorialinator was an exercise in discovering what matters through failure. The system that exists now is meaningfully different from what was imagined on day one — not because the vision changed, but because the implementation taught lessons about what the vision actually required.

What worked well:

Single-file HTML — the portability argument proved out. Send the file, open it, done. No install, no server, no build step. This is the feature people notice first.

Locked design system — taking away visual decisions from the LLM was the highest-leverage change. Output quality jumped immediately.

Self-healing install — the auto-setup and install scripts handle edge cases automatically. Building something like this was super cool. Using it is so much easier — you pull it down from GitHub with the curl, it runs the installation script, that's self-healing... once it's ready you restart and then you can go from there.

Local-first processing — trust by default. Users are more willing to process sensitive recordings when the data stays on their machine.

What didn't:

Quiz quality in video mode — the most educationally significant failure. The agent grounds quiz questions in what was said rather than what should be learned. This requires ongoing prompt refinement.

Sandbox omission for non-code topics — the agent needs explicit guidance that "sandbox" doesn't mean "code editor." It means "structured input area relevant to the topic."

Truth and accuracy — the LLM occasionally generates content not present in the source video. The hardest problem to solve structurally.

Output token limits — phased generation works but adds complexity and occasional seam artifacts between phases.

How prompts evolved:

The prompt evolution followed a pattern: generate, evaluate, identify failure, add constraint, regenerate. The initial SKILL.md was mostly design system spec — generated tutorials looked good but taught poorly. Adding Bloom's taxonomy requirements improved topic-mode quiz quality but not video-mode. Adding the pedagogical review sub-agent caught scaffolding gaps but the recall quiz problem persisted. Adding an explicit check ("Can this be answered without watching the video?") helped, but video-mode quizzes are still the weakest dimension.

The lesson: prompt engineering for complex systems isn't about writing one great prompt. It's about building a feedback loop where failures inform constraints, and constraints accumulate into a robust specification.

Would I keep using this system?

Yes, with caveats. The system is genuinely useful for its intended purpose. Recording a video walkthrough and getting an interactive tutorial in return is a meaningful time saver — especially for internal team knowledge sharing where "good enough" quality is fine and the alternative is a Loom that nobody watches twice.

The caveats are real: you still need to review the output for accuracy (especially in video mode), the sandbox gap means some tutorials need manual touchup, and the benchmark shows a 67% pass rate — not 100%. But the 67% that pass are genuinely good, and the 33% that fail are fixable through iteration.

The most promising direction is a self-improvement loop: embedding the benchmark rubric into the skill itself so the agent can score its own output, identify gaps, and refine in a second pass. The benchmark log tables in tutorialinator-benchmark.md are designed for exactly this — one-shot scores followed by two-shot refinements.
