The Problem

The N×M integration nightmare

Imagine you have 5 AI assistants (Claude, ChatGPT, Copilot, Cursor, Gemini) and 8 data sources (GitHub, Slack, PostgreSQL, Google Drive, Jira, etc). Without a standard, each AI needs a custom integration for each source. That's 5 × 8 = 40 integrations to build and maintain.

MCP flips this to M + N. Each AI implements one MCP client. Each data source implements one MCP server. Now it's 5 + 8 = 13 components. Any client talks to any server. That's the entire pitch.

Definition

MCP is USB-C for AI

Model Context Protocol (MCP) is an open standard created by Anthropic in November 2024 for connecting AI applications to external tools and data. Think of it like USB-C for AI — a universal port that any AI app can use to plug into any data source.

It's now governed by the Agentic AI Foundation under the Linux Foundation, co-founded by Anthropic, Block, and OpenAI. It's not locked to Claude — it works with ChatGPT, VS Code Copilot, Cursor, JetBrains, and any app that implements the protocol.

Primitives

Tools, Resources & Prompts

An MCP server can expose three types of capabilities. Each has a distinct purpose and a different actor that controls it. Understanding which to use when is one of the trickiest parts of MCP design.

⚙

Tools

Executable functions the AI can call. Think: "search flights", "create issue", "run query". The model decides when to use them based on the conversation.

tools/list tools/call

📄

Resources

Read-only data that provides context. Think: file contents, database schemas, API docs. The application decides when to fetch them — the AI doesn't call them directly.

resources/read resources/list

💬

Prompts

Reusable templates that structure interactions. Think: slash commands. The user invokes them explicitly — neither the AI nor the app decides automatically.

Comparison

MCP vs REST APIs

MCP doesn't replace REST. It complements it. An MCP server often calls REST APIs under the hood. REST is the backbone of service-to-service communication. MCP is the AI orchestration layer that makes those services accessible to language models.

REST API
Designed forAny consumer (apps, humans, services)
CommunicationRequest → Response (one way)
StateStateless by design
DiscoveryDeveloper reads docs, hardcodes endpoints
SchemaRequires separate OpenAPI/Swagger spec
ProtocolHTTP with REST conventions
MCP
Designed forAI agents and LLMs specifically
CommunicationBidirectional (server can push notifications)
StateStateful sessions with capability negotiation
DiscoveryAI asks "What can I do?" at runtime
SchemaTools self-describe with JSON Schema
ProtocolJSON-RPC 2.0 over stdio or HTTP

Anatomy

What the SDK handles for you

Good news: you don't implement JSON-RPC from scratch. The @modelcontextprotocol/sdk package handles the protocol layer — initialization, capability negotiation, message framing, transport. You just write tool logic.

A minimal MCP server has three parts:

1

Create server

Instantiate McpServer with a name and version. This is your server's identity during the handshake.

2

Register tools

Define what your server can do. Each tool gets a name, description, input schema (Zod), and a handler function.

3

Connect transport

Attach a transport (stdio for local, HTTP for remote) and start listening. One line of code.

Prerequisite

JSON Schema in 30 seconds

Before building your server, you need to know how input schemas work. When you register a tool, you define what parameters it accepts using Zod (the TypeScript SDK converts it to JSON Schema automatically). Here's a quick mapping:

ZOD (WHAT YOU WRITE)
z.object({
  text: z.string()
    .describe("Input text"),
  limit: z.number()
    .optional()
    .describe("Max chars")
})
JSON SCHEMA (WHAT THE AI SEES)
{
  "type": "object",
  "properties": {
    "text": { "type": "string" },
    "limit": { "type": "number" }
  },
  "required": ["text"]
}

The .describe() string becomes the description the AI reads to understand each parameter. The better the description, the smarter the AI's tool usage.
